# 微信与支付宝交易识别规则

本文记录当前 Android 客户端已经实现的交易识别规则。结构按“平台 → 识别入口 → 交易类型”展开，描述的是现行代码行为，不代表支付平台的全部页面或通知都已覆盖。

## 1. 通用边界

### 1.1 支持的平台与入口

- 微信：仅接受包名 `com.tencent.mm`。
- 支付宝：仅接受包名 `com.eg.android.AlipayGphone`。

- 交易发生时自动识别：
  - 通知监听读取微信、支付宝通知。
  - 开启自动记账功能后，无障碍服务观察支付完成页；微信无障碍节点文本不可用时可走受限的本机OCR。

- 账单补录：
  - 用户从“待确认 → 补录账单”主动选择平台。
  - 微信补录只读取本机OCR结果。
  - 支付宝补录只读取当前页面的无障碍节点文本，不使用截图 OCR。

所有识别结果都只会先进入“待确认”。补录每次只读取当前可见页面，不自动滚动、翻页或扫描完整历史。

### 1.2 金额与收支方向

- 页面详情与OCR：金额必须带 `¥`、`￥` 或 `元`；下文所述规范化列表行可以只写数字。金额正负号不会改变识别出的绝对金额。
- 通知：优先读取带 `¥`、`￥` 或 `元` 的金额；没有货币标记时，标题与正文合并后必须只有一个数字才可作为金额。
- 页面同时出现余额、优惠、折扣、抵扣、红包抵扣、积分或手续费时，这些金额默认不作为交易金额；`交易金额`、`付款金额`、`收款金额`、`转账金额`、`红包金额`、`实付`、`实收`、`金额` 标注的金额优先。
- `收入`、`退款`记为流入；其他类型默认记为流出。明确的红包和转账方向会优先转成`收入`或`支出`，不会保留为无方向的`红包`或`转账`。

### 1.3 通知的共同触发条件

微信和支付宝通知使用同一套正文规则，只通过包名确定平台。必须同时满足：

1. 含有至少一个交易词：`支付`、`付款`、`收款`、`到账`、`交易`、`转账`、`红包`、`退款`、`扣款`、`消费`。
2. 含有金额，或者含有至少一个结果词：`成功`、`到账`、`退款`、`转账`、`红包`、`已支付`、`已付款`。
3. 能解析出唯一金额。
4. 能按下述优先级判断交易类型。

交易类型按顺序匹配，命中前一项后不再继续：

1. 含`退款` → `退款`。
2. `收到`同时搭配`红包`或`转账`，或者含`向你转账` → `收入`。
3. 含`收款`或`到账` → `收入`。
4. 含`发出红包`、`红包已发出`、`转账给`，或者匹配“向某人转账”但不是“向你转账” → `支出`。
5. 含`付款`、`支付成功`、`付款成功`或`已支付` → `支出`。
6. `支出`与`交易`同时出现 → `支出`。

无法判断类型时，即使通知看起来与支付有关，也不创建待确认项。

## 2. 微信

### 2.1 交易发生时：通知识别

除通用通知条件外，微信各交易类型的判断如下：

| 交易类型 | 必须出现的方向证据 | 识别结果 | 对方/商户提取 |
| --- | --- | --- | --- |
| 商户支付 | `付款`、`支付成功`、`付款成功`、`已支付`之一 | 支出 | 优先读取`商户：...`，或成功词与金额之间的名称 |
| 商户收款 | `收款`或`到账` | 收入 | 无法提取时使用“未知来源” |
| 收到转账 | `收到...的转账`或`...向你转账` | 收入 | 提取转账人 |
| 发出转账 | `转账给...`或`向...转账`，且对象不是“你” | 支出 | 提取收款人 |
| 收到红包 | `收到...的红包` | 收入 | 提取发红包的人 |
| 发出红包 | `发出红包`或`红包已发出` | 支出 | 对方统一记为“红包” |
| 退款 | 含`退款` | 退款 | 优先级最高；无法提取时使用“未知来源” |

以上各行仍服从 1.3 节的先后顺序。例如同一通知同时含`收款`和`支付成功`时，当前代码先判为`收入`。

### 2.2 交易发生时：支付结果页识别

微信自动页面识别只接受完成态页面，不把普通聊天页或微信历史账单列表作为自动捕获入口。

#### 商户支付

必须同时满足：

- 页面先出现`支付成功`，其后出现`返回商家`。
- 页面含明确金额。
- 页面不含付款发起词或活动聊天输入控件。

解析结果为`支出`。商户优先从商品、商户或金额附近标题提取；缺失时使用“微信支付”。

#### 发出转账

必须同时满足：

- 页面含`转账成功`，或者匹配`待...确认收款`。
- 页面含支付完成词和明确金额。
- 页面不含付款发起词、普通聊天页特征或活动聊天输入控件。

`转账成功`、`对方已收 + 转账`、`转账给...`或`向...转账`会判为`支出`；对方优先从`待...确认收款`、`转账给...`或`向...转账`提取。

#### 收到红包

必须按顺序出现：

1. `...的红包`标题。
2. 标题之后出现红包金额。
3. 金额之后出现`已存入零钱`。
4. 随后出现`回复表情到聊天`。

同时不能出现活动聊天输入控件。满足后判为`收入`。

#### 发出红包

满足以下任一完整详情签名：

- `...的红包` → `红包金额...元，等待对方领取` → `未领取的红包，将于24小时后发起退款`。
- `...的红包` → `N个红包共...元`，并在领取明细中同时出现领取金额和 `HH:mm` 时间。

同时必须含明确金额且不能出现活动聊天输入控件。满足后判为`支出`，对方标题统一记为“红包”。

#### 退款

- 通知入口支持独立的`退款`类型。
- 微信自动页面入口当前没有独立的退款完成页签名；只有页面同时满足上述商户支付、转账或红包完成态入口时，解析器才可能再按`退款`优先级识别。
- 需要稳定补录微信退款时，使用下文“账单补录 → 退款”规则。

#### 微信自动 OCR 的附加条件

自动OCR不是新的交易规则，只在微信无障碍节点为空或仅含通用按钮文字时补足页面文本，并要求：

- Android 11 及以上、屏幕亮起且未锁定。
- 页面命中上述商户支付、转账或红包完整签名。
- 当前窗口是应用窗口。
- 商户支付、转账、红包各有受信任的结果页 Activity；若 Activity 不受信任，还必须能与最近 5 分钟内同商户、同金额、同类型的微信通知匹配。

### 2.3 账单补录：微信 OCR

微信补录只在用户选择微信后，对当前补录会话中的可见页面执行本机OCR。它不读取微信无障碍节点中的账单字段，也不要求命中特定 Activity。

#### 商户支付支出

必须同时识别到：

- `当前状态`
- `支付成功`
- 一个无歧义交易金额

识别结果为`支出`。`账单服务`不是触发条件；若 OCR 识别到该行，会在后续解析前移除。

#### 发出转账

必须同时识别到：

- `当前状态`
- `对方已收`
- 一个无歧义交易金额

`对方已收钱`也满足，因为它包含`对方已收`。后续页面文本还需含`转账`上下文，才能稳定判为`支出`并提取对方。

为容忍已确认的 OCR 常见误差，代码会先做以下修正：

- `对方己收` → `对方已收`
- `对方已收线` → `对方已收钱`

#### 退款

必须同时识别到：

- `退款状态`
- `已退款`
- 一个无歧义交易金额

识别结果为`退款`，资金方向为流入。

#### 微信补录统一拒绝条件

即使正面关键词和金额都已出现，只要页面还含以下任一词就拒绝：

`确认支付`、`立即支付`、`收银台`、`支付密码`、`待支付`、`处理中`、`支付失败`、`已取消`。

当前微信补录没有为“收到转账”“收到红包”“发出红包”配置独立放行签名，因此这些页面不能仅凭对应方向词通过补录入口。

## 3. 支付宝

### 3.1 交易发生时：通知识别

支付宝通知与微信通知使用相同的通用触发条件和类型优先级：

| 交易类型 | 必须出现的方向证据 | 识别结果 |
| --- | --- | --- |
| 商户支付 | `付款`、`支付成功`、`付款成功`、`已支付`之一 | 支出 |
| 收款到账 | `收款`或`到账` | 收入 |
| 收到转账 | `收到...的转账`或`...向你转账` | 收入 |
| 发出转账 | `转账给...`或`向...转账`，且对象不是“你” | 支出 |
| 退款 | 含`退款` | 退款 |
| 支出摘要 | `支出`与`交易`同时出现 | 支出 |

以上各行仍服从 1.3 节的先后顺序。

通知中没有付款账户时，资金账户回退为“支付宝余额”；没有商户或对方时，标题回退为“未知来源”。

代码的通知关键词层也能识别`收到...的红包`、`发出红包`和`红包已发出`，但当前没有支付宝红包页面的专用完成态校验。

### 3.2 交易发生时：无障碍页面识别

支付宝自动页面识别使用无障碍节点文本，不使用截图 OCR。

#### 支付、收款、转账与退款完成页

必须同时满足：

1. 含明确金额。
2. 含至少一个完成词：`支付成功`、`付款成功`、`交易成功`、`转账成功`、`收款成功`、`退款成功`、`红包发送成功`、`已支付`或`已付款`。
3. 含至少一个支付宝结果页上下文：`收款方`、`付款方式`、`支付方式`、`交易时间`、`订单号`、`交易单号`、`支付信息`、`支付凭证`、`交易详情`、`账单详情`、`查看账单`或`返回首页`。
4. 能按通用页面类型规则判断为`支出`、`收入`、`退款`、`转账`或`红包`。

类型判断重点：

- 含`退款` → `退款`。
- `收入`、`收款到账`、`收款成功`、`入账`、`收到...转账/红包`或`向你转账` → `收入`。
- `支出`、`付款`、`支付成功`、`交易成功`、`转账成功`、`扫码支付`、`碰一碰支付`、`转账给...`或`向...转账` → `支出`。
- 只有`红包`或`转账`而没有方向证据时，分别保留为`红包`或`转账`，默认资金方向为流出，等待用户在“待确认”修正。

#### 支付记录或消息中心记录

非完成页必须同时满足：

- 页面含明确金额。
- 页面含账单、交易记录、支付记录、收支明细、账单详情、交易详情、支付信息、支付凭证、消息盒子等记录上下文。
- 每条记录含可识别的交易时间和类型。
- 能提取商户/收款方；若完成页缺失对方可回退为“支付宝支付”，普通记录页不能只靠该回退创建记录。

支付宝“交易记录”总览页只要出现`搜索交易记录`，或同时出现`收支分析 + 筛选 + 全部`，自动监控就明确忽略，避免滚动列表误触发。支付消息中心或单条详情仍可识别。

### 3.3 账单补录：支付宝无障碍文本

用户选择支付宝后，补录会话读取当前可见页面的无障碍节点文本，不调用截图 OCR。支持两类输入：

#### 单条详情或当前记录页

- 页面必须是账单/交易/支付记录上下文，或者满足支付宝完成页条件。
- 必须有明确金额和可判断的交易类型。
- 普通历史记录必须有明确交易时间；完成页没有时间时可使用本次捕获时间。
- 普通历史记录必须能提取商户/收款方；完成页缺失时回退为“支付宝支付”。
- 支出、收入、转账、退款和无方向红包的判断词与上一节一致。

#### 规范化列表行

页面出现以下格式的完整单行时可直接解析：

`YYYY-MM-DD HH:mm 商户 类型 金额 [资金账户]`

其中类型只接受`支出`、`收入`、`退款`、`转账`、`红包`、`还款`、`投资`、`手续费`；资金账户缺失时回退为“支付宝余额”。

### 3.4 支付宝页面统一拒绝条件

页面含付款发起词时不识别：`收银台`、`立即付款`、`确认付款`、`确认支付`、`支付密码`、`输入密码`、`添加转账说明`。

普通聊天或消息页默认拒绝；只有同时命中`支付信息`、`支付凭证`、`消息盒子`、`交易详情`、`账单详情`等支付消息中心上下文时才继续判断。

## 4. 结果字段与优先级说明

- 识别成功后尽量保留：平台、商户/对方、金额、类型、交易时间、付款方式/资金账户、商品或备注、交易单号、商户单号。
- 页面类型优先级是：微信红包完整签名 → 退款 → 微信已完成转账/支付 → 收入词 → 支出词 → 无方向红包/转账。
- 通知类型优先级是：退款 → 收到红包/转账 → 发出红包/转账 → 收款到账 → 付款支付 → 支出摘要。
- 页面或通知只要缺少金额、类型或必需的完成态上下文，就不会创建待确认项。
- 新候选还会经过已确认账本和待确认队列的去重；重复项可能跳过、合并或标为“疑似重复”。
