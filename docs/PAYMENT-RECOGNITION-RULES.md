# 微信与支付宝交易识别规则

本文记录当前 Android 客户端的手动账单补录规则。结构按“平台 → 手动入口 → 交易类型”展开，描述的是现行代码行为，不代表支付平台的全部页面都已覆盖。

## 1. 通用边界

### 1.1 支持的平台与入口

- 微信：仅接受包名 `com.tencent.mm`。
- 支付宝：仅接受包名 `com.eg.android.AlipayGphone`。
- 用户从“待确认 → 补录账单”主动选择平台并建立一次性导入会话。
- 微信补录只使用本机会话内 OCR；支付宝补录只读取当前页面的无障碍节点文本，不使用截图 OCR。
- 每次只读取当前可见页面，不自动滚动、翻页或扫描完整历史。
- 所有识别结果都只会先进入“待确认”，不会直接写入账本。

### 1.2 金额与收支方向

- 页面详情与 OCR：金额必须带 `¥`、`￥` 或 `元`；规范化列表行可以只写数字。
- 页面同时出现余额、优惠、折扣、抵扣、红包抵扣、积分或手续费时，这些金额默认不作为交易金额；`交易金额`、`付款金额`、`收款金额`、`转账金额`、`红包金额`、`实付`、`实收`、`金额` 标注的金额优先。
- `收入`、`退款`记为流入；其他类型默认记为流出。明确的红包和转账方向会优先转成`收入`或`支出`，不会保留为无方向的`红包`或`转账`。

### 1.3 统一拒绝条件

页面含付款发起词时不识别：`收银台`、`立即付款`、`确认付款`、`确认支付`、`支付密码`、`输入密码`、`添加转账说明`、`待支付`、`处理中`、`支付失败`、`已取消`。

普通聊天、消息页和不支持的页面默认拒绝。页面必须具备支付/账单上下文、明确金额和可判断的交易类型。

## 2. 微信手动 OCR 补录

微信补录只在用户选择微信后，对当前补录会话中的可见页面执行本机 OCR。它不读取微信无障碍账单字段，也不要求命中特定 Activity。

### 2.1 商户支付支出

必须同时识别到：

- `当前状态`；
- `支付成功`；
- 一个无歧义交易金额。

识别结果为`支出`。`账单服务`不是触发条件；若 OCR 识别到该行，会在后续解析前移除。

### 2.2 发出转账

必须同时识别到：

- `当前状态`；
- `对方已收`；
- 一个无歧义交易金额。

`对方已收钱`也满足，因为它包含`对方已收`。后续页面文本还需含`转账`上下文，才能稳定判为`支出`并提取对方。

### 2.3 退款

必须同时识别到：

- `退款状态`；
- `已退款`；
- 一个无歧义交易金额。

识别结果为`退款`，资金方向为流入。

### 2.4 文字容错

为容忍已确认的 OCR 常见误差，代码会先做以下修正：

- `对方己收` → `对方已收`；
- `对方已收线` → `对方已收钱`。

即使正面关键词和金额都已出现，只要页面命中统一拒绝条件，就拒绝页面。

## 3. 支付宝手动无障碍补录

用户选择支付宝后，补录会话读取当前可见页面的无障碍节点文本，不调用截图 OCR。

### 3.1 单条详情或当前记录页

- 页面必须是账单、交易或支付记录上下文，或者满足支付宝完成页条件。
- 必须有明确金额和可判断的交易类型。
- 普通历史记录必须有明确交易时间；完成页没有时间时可使用本次捕获时间。
- 普通历史记录必须能提取商户/收款方；完成页缺失时回退为“支付宝支付”。
- 支出、收入、转账、退款和无方向红包的判断词与通用规则一致。

### 3.2 规范化列表行

页面出现以下格式的完整单行时可直接解析：

`YYYY-MM-DD HH:mm 商户 类型 金额 [资金账户]`

其中类型只接受`支出`、`收入`、`退款`、`转账`、`红包`、`还款`、`投资`、`手续费`；资金账户缺失时回退为“支付宝余额”。

## 4. 结果字段与优先级

- 识别成功后尽量保留：平台、商户/对方、金额、类型、交易时间、付款方式/资金账户、商品或备注、交易单号、商户单号。
- 页面类型优先级是：退款 → 微信已完成转账/支付 → 收入词 → 支出词 → 无方向红包/转账。
- 页面只要缺少金额、类型或必需的完成态上下文，就不会创建待确认项。
- 新候选还会经过已确认账本和待确认队列的去重；重复项可能跳过、合并或标为“疑似重复”。
